# calendar.onnenai.cc — アイデア仕様書

Claude Code にそのまま渡して実装するための仕様書。まずこのファイル全体を読んでから着手すること。

> **注意:** この仕様を実装レベルに落とした `docs/DESIGN.md` があり、食い違う箇所は DESIGN.md（さらに見た目・文言は Figma）が優先する。特に D1〜D5（範囲・キャッシュ・Secret・スタック・OAuth）を必ず読むこと。

## 1. これは何か / なぜ作るか

- 自分の Google カレンダーを、**予定の詳細を一切見せず「いつ埋まっているか」だけ**いろんな人に公開するページ。
- 空き時間を聞かれたら、この URL を渡すだけで済むようにするのが目的。嬉しさはそこに集約する。
- 公開先ドメイン: `calendar.onnenai.cc`
- ステータス表示（今どこにいるか等）は **やらない**。それは Misskey で十分。ページ隅に Misskey へのリンクだけ置く。
  - Misskey: https://social.onnenai.cc/@onnel

## 2. MVP のスコープ

やること:

- 複数の Google カレンダーを合体し、埋まっている時間帯だけを週表示で見せる
- 表示範囲は「今日から 14 日間」（今週＋来週相当）。過去は出さない、15 日以上先も出さない
- 時刻は **30 分単位に丸める**（開始は切り捨て、終了は切り上げ）
- レスポンシブ対応（スマホでは日ごとのリスト表示に切り替える）

やらないこと（Non-goals）:

- 予定の予約・リクエスト受付（Calendly 的な機能は不要）
- ステータス表示、現在地、最終更新以外のリアルタイム情報
- 予定のタイトル・場所・参加者・メモの表示や取得
- ログイン機能、管理画面（設定は全部サーバー側の定数／環境変数で済ませる）

## 3. プライバシー要件（最重要・絶対条件）

1. Google Calendar API は **FreeBusy API (`freebusy.query`) のみ** を使うこと。
   `events.list` / `events.get` は使わない。FreeBusy は開始／終了時刻しか返さないので、タイトル等が構造的に漏れない。
2. API レスポンス（自前 JSON）に含めてよいのは、丸め済みの `start` / `end` と生成時刻だけ。
   カレンダー名・カレンダー ID もフロントには出さない。
3. 表示範囲の制限は **サーバー側で強制** する。クライアントからのパラメータで範囲を広げられないこと。
   週切り替えも「今週」「来週」の 2 択までに制限する。
4. 認証情報（リフレッシュトークン等）は Worker の Secret に置き、コードやリポジトリに絶対に含めない。
5. ログに予定情報を残さない（FreeBusy の時刻情報も含め、原則ログしない）。

## 4. 対象カレンダー

所有者の Google アカウントから見える以下の 4 つを合体する（ID は `CALENDAR_IDS` 環境変数にカンマ区切りで設定し、コードに直書きしない）。

> 実際の ID はリポジトリに置かない（D3）。`.dev.vars` と `wrangler secret put CALENDAR_IDS` にだけ設定する。値はユーザーが持っている。

| 表示名（内部用） | Calendar ID |
|---|---|
| メイン (primary) | `<primary の Gmail アドレス>` |
| グループ 1 | `<グループカレンダーID>` |
| グループ 2 | `<グループカレンダーID>` |
| 共有カレンダー（他アカウント所有・読み取り専用） | `<共有元アカウントのアドレス>` |

- 共有カレンダーは他アカウント所有で読み取り専用だが、所有者アカウント経由の FreeBusy クエリ対象には含められる想定。もし取得できない場合は、そのカレンダーだけ除外して他を正常に表示し、エラーで全体を落とさないこと。

## 5. アーキテクチャ

本人の既存構成（Cloudflare / TypeScript）に合わせる。

- **バックエンド**: Cloudflare Workers（TypeScript）
  - Google OAuth のリフレッシュトークンでアクセストークンを取得（スコープは最小限: `https://www.googleapis.com/auth/calendar.freebusy`）
  - サービスアカウント方式は不可（他アカウント所有の共有カレンダーをサービスアカウントに共有できないため）。所有者アカウントの OAuth を使う
  - 結果は **15 分キャッシュ**（Cache API または KV）。Google API を毎リクエスト叩かない
- **フロントエンド**: Astro（静的）＋ 必要最小限のクライアント JS。Cloudflare Pages か Workers の静的配信、どちらでも可
- **DNS**: `calendar.onnenai.cc` を Cloudflare で向ける

### 環境変数 / Secret

```
GOOGLE_CLIENT_ID          # OAuth クライアント ID
GOOGLE_CLIENT_SECRET      # Secret
GOOGLE_REFRESH_TOKEN      # Secret
CALENDAR_IDS              # 上記 4 つの ID（カンマ区切り）
TIMEZONE=Asia/Tokyo
```

リフレッシュトークンの取得手順（OAuth Playground か小さなスクリプトで一度だけ）も README に書くこと。

## 6. API 設計（自前）

```
GET /api/busy?week=0   # 今週（今日を含む週）
GET /api/busy?week=1   # 来週
```

- `week` は 0 / 1 のみ受理。それ以外は 0 扱いか 400。
- ただしサーバー側の絶対上限として「今日 00:00 (JST) 〜 14 日後 23:59 (JST)」を超える範囲は絶対に返さない。

レスポンス例:

```json
{
  "timezone": "Asia/Tokyo",
  "generatedAt": "2026-11-25T10:00:00+09:00",
  "busy": [
    { "start": "2026-11-26T09:00:00+09:00", "end": "2026-11-26T10:30:00+09:00" },
    { "start": "2026-11-26T13:00:00+09:00", "end": "2026-11-26T14:30:00+09:00" }
  ]
}
```

### 加工ロジック

1. FreeBusy で全カレンダーの busy 区間を取得
2. 各区間を 30 分単位に丸める（start = 30 分に切り捨て、end = 30 分に切り上げ）
3. 全カレンダー分をマージし、重なる／隣接する区間を 1 つに結合
4. 範囲外（過去・15 日目以降）を切り捨て
5. 終日予定は FreeBusy 上は 0:00〜翌 0:00 の区間として来る想定。そのまま「終日埋まっている」表示でよい（実装時に実データで確認すること）

## 7. 画面仕様

- ヘッダー: ページ名（仮でよい）＋ 一文説明
  - 文案: 「予定の詳細は公開していません。埋まっている時間帯だけを表示しています。」
- 週グリッド表示:
  - 7 日分（月曜始まり）、時間軸は 8:00〜24:00 を主表示（範囲外の区間は端でクリップし、あること自体は分かるようにする）
  - 埋まっている区間は単色ブロックで表示し、ラベルは付けない（「予定あり」以外の文字をブロック内に出さない）
  - 「今週 / 来週」切り替えボタン
  - 現在時刻のライン表示があると嬉しい（任意）
- スマホ表示: 日ごとのリスト（例:「11/26（水） 09:00–10:30 / 13:00–14:30」）。区間がない日は「予定なし」
- フッター: 「最終更新: ○○」＋ Misskey リンク
- デザイン: シンプルで読みやすく。ライト／ダーク両対応。凝った装飾は不要、実用優先

## 8. エラー処理

- 1 カレンダーだけ取得失敗 → その分を除いて表示継続。フロントには失敗を出さない
- 全カレンダー失敗 or Google API ダウン → キャッシュがあればキャッシュを返し、なければ「情報を取得できませんでした」とだけ表示（詳細エラーは出さない）
- レート制限を避けるため、キャッシュなしでも Google API へのリクエストは 15 分に 1 回まで

## 9. 実装の順番（Claude Code 向け）

1. プロジェクト雛形作成（Astro + Cloudflare Workers、TypeScript）
2. まずモックデータで画面（週グリッド＋スマホリスト）を完成させる
3. Worker 側で FreeBusy 取得 → 丸め → マージ → キャッシュを実装
4. `.env.example` と README（トークン取得手順・デプロイ手順・DNS 設定）を作成
5. 実データで終日予定・繰り返し予定・範囲外予定の挙動を確認
6. デプロイし、`calendar.onnenai.cc` で表示確認

## 10. 受け入れ条件

- [ ] ページの HTML / JS / ネットワークレスポンスのどこにも、予定名・場所・参加者・カレンダー名が含まれていない
- [ ] 取得に使っている Google API が FreeBusy のみである（コード上で確認できる）
- [ ] 今日より前と 15 日以上先の区間が、パラメータをいじっても取得できない
- [ ] 時刻がすべて 30 分単位に丸まっている
- [ ] 重なった予定が 1 つのブロックにマージされている
- [ ] 共有カレンダーなど 1 カレンダーが失敗してもページが表示される
- [ ] スマホで日ごとリスト表示になる
- [ ] 認証情報がリポジトリに含まれていない（Secret 管理になっている）
